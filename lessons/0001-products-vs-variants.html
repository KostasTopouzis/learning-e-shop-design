Lesson 0001 · Catalog data model

What do you actually sell?

Products, options and variants: the first tables in The Edit's database.

≈ 15 minPrereq: basic SQLRef: Catalog data model

Your win today

Write the Postgres tables for The Edit's catalog, and be able to explain in one sentence why the cart points at a variant and not a product.

The problem

A shopper on The Edit opens the Linen Shirt page, picks Navy and M, and clicks Add to bag. Your products table has one row: "Linen Shirt". What does the cart save?

If it saves the product ID, you've lost the colour and the size. And you can't answer the questions the business will ask next: Is Navy/M in stock? Does XL cost more? Which barcode does the warehouse scan? Each of those has a different answer for each colour/size combination. The "Linen Shirt" isn't one thing you sell. It's a family of things you sell.

Three concepts

Every serious commerce platform splits the catalog the same way. Shopify's developer docs put it like this:[1]

ConceptWhat it isThe Edit example
Product"The container for all product information (title, description, vendor)."Linen Shirt
Option"Characteristics customers choose from, like color or size." Each option has a name and a list of values.Color: Navy, White, Sand
Size: S, M, L, XL
Variant"Specific purchasable SKUs representing combinations of option values."Linen Shirt / Navy / M

The rule that matters most for your database: money and stock live on the variant. Shopify: "each variant has its own price, inventory, and barcode."[1] Saleor says it more strongly:

"Checkout and orders can only contain variants." … "Prices and stock can only be assigned at a variant level." Saleor, Product Overview [2]

So the product holds the shared description (what's on the page) and the variant is the unit of sale (what goes in the bag, gets charged, and leaves the warehouse). A SKU (stock-keeping unit) is the business's ID for one variant, e.g. LS-NAVY-M.

Products with no options: a tote bag still gets one variant. Shopify creates a "standalone" default variant automatically for this reason.[3] Your cart, orders and inventory then only ever deal with one kind of thing, so there's no special case.

As tables

This is the same shape as the open-source engines. In Medusa's docs, options are a product's available attributes and variants are the salable combinations of them. They also forbid two variants with the same option values.[4]

Practice 2 · Recall

Answer from memory. Don't scroll up.

1. A shopper adds "Linen Shirt, Navy / M" to the bag. The cart line should store…

The variant ID pins down the colour, size, price and stock in one reference. "Checkout and orders can only contain variants."

2. The Linen Shirt has 3 colours and 4 sizes. At most how many variants can it have?

Variants are combinations: 3 × 4 = 12. Each new option multiplies the count. That's why Shopify has to publish a hard cap (2,048 per product).[3] You can also leave out combinations you don't make. Then you have fewer variants, not more.

3. Why do price and stock live on the variant?

Navy/M can sell out on its own and XL can cost more on its own. A value that can differ per combination belongs to the combination.

4. A tote bag comes in one style only. How many variants should it have?

One default variant keeps carts, orders and inventory uniform. They always reference a variant, with no special case. Shopify auto-creates this "standalone" variant.

Your turn · The Edit

Open your repo and write a migration (a plain .sql file is fine, or Prisma/Drizzle if you've chosen one) with the five tables above. Before you peek at the answer, decide:

  1. Which columns must be unique? (Think URLs and warehouse codes.)
  2. Which columns need a check constraint so bad data can't get in?
  3. What happens to variants when a product is deleted?
Compare with a reference version 
create table products (
  id          bigint generated always as identity primary key,
  handle      text not null unique,          -- /products/linen-shirt
  title       text not null,
  description text,
  brand       text,
  created_at  timestamptz not null default now()
);

create table product_options (
  id         bigint generated always as identity primary key,
  product_id bigint not null references products(id) on delete cascade,
  name       text not null,                  -- 'Color', 'Size'
  position   int  not null default 0,        -- display order
  unique (product_id, name)
);

create table product_option_values (
  id        bigint generated always as identity primary key,
  option_id bigint not null references product_options(id) on delete cascade,
  value     text not null,                   -- 'Navy', 'M'
  unique (option_id, value)
);

create table product_variants (
  id          bigint generated always as identity primary key,
  product_id  bigint not null references products(id) on delete cascade,
  sku         text not null unique,          -- 'LS-NAVY-M'
  price_cents integer not null check (price_cents >= 0),
  stock       integer not null default 0 check (stock >= 0)
);

create table variant_option_values (
  variant_id      bigint not null references product_variants(id) on delete cascade,
  option_value_id bigint not null references product_option_values(id) on delete cascade,
  primary key (variant_id, option_value_id)
);

Two choices here we'll revisit (they make good interview talking points):

  • price_cents integer: money stored as whole cents, never as a float. This gets its own lesson.
  • stock as a column on the variant is a starting point. Real systems move it to a separate inventory table, which Medusa links from each variant.[4] That's what makes multiple warehouses and reservations possible.
  • on delete cascade on products is fine while you prototype. In a live shop you'd rarely hard-delete a product that appears in past orders. You'd archive it instead. More on that in the orders lesson.

See the constraint syntax in the PostgreSQL docs.

Done when

The migration runs against your Postgres. You've inserted the Linen Shirt with 2 options and at least 4 variants. And you can say out loud: "The product is what you browse, the variant is what you buy."
