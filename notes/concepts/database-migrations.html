Database migrations

A versioned file that changes your database's structure from one version to the next, saved in your repo and run in order.

Asked: "What does 'migration' mean, and why use it?"Updated 2026-10-25

What a migration is

A migration is a file that changes your database's structure (its schema) from one version to the next. It's saved in your repo and run in order.

"A controlled set of changes that modify and evolve the structure of your database schema." Prisma, Understanding Migrations

For The Edit, it would look like this over time:

migrations/
  0001_create_catalog.sql        ← lesson 1: products, options, variants
  0002_create_carts.sql          ← later: carts, cart_lines
  0003_add_compare_at_price.sql  ← later: "was £60, now £45"

Each file describes only the change: create table …, alter table … add column …. To build the database, you run them one after another.

How the database knows what's already been run

Migration tools record which files have been applied, in a bookkeeping table inside the database itself. Prisma, for example, uses a _prisma_migrations table and treats your migrations/ folder as "the source of truth for the history of your data model" (Prisma: Migration histories).

So when you run "migrate", the tool:

  1. looks at which migrations the database has already recorded,
  2. runs only the new ones, in order,
  3. records them as done.

Why it matters

Without migrations, you'd change your database by typing SQL into a console. That works on your laptop, then goes wrong as soon as there's a second database. The Edit will have several:

  • your local Postgres while you develop,
  • the production database behind your live Vercel site,
  • possibly a preview database for Vercel preview deployments.

With migrations, all of them get the same schema by running the same files in the same order. It's version control for your database structure, and it's reviewable in pull requests just like code.

Why the lesson says "migration"

I want your schema to start out as a migration file, not as SQL you type once into a console. It's how professional teams work, and an interviewer will notice it in your repo.

Two rules worth knowing early

  1. Never edit a migration that has already been applied (especially in production). Write a new one that makes the further change. Prisma even warns if an applied migration has been edited.
  2. Migrations change structure, and they can affect data. For example, dropping a column deletes that data. Changing a live schema safely is a real skill. We'll touch on it when The Edit has real orders worth protecting.

In practice

A plain 0001_create_catalog.sql file run with psql counts as a migration. A tool like Prisma Migrate or Drizzle Kit generates and tracks these files for you. Choosing one is a decision for when The Edit moves to Next.js.
